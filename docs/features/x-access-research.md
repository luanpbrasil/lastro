# X post access: technical research

Researched: 2026-11-12. Status: evidence for discovery, not an implementation decision.

Scope: an explicit Lastro action beside one selected X post; only that post's own written text, within Lastro's economics/politics context. Thread context, embedded quoted-post content, attached images/video/audio are excluded. See [confirmed scope](x-integration.md).

## Chrome page access

- Chrome content scripts can read and modify a page's DOM and communicate with the extension. Their isolated JavaScript environment does not give access to the page's JavaScript variables; isolation does not make the shared DOM an authenticated record. Static injection uses URL match patterns. [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)
- Programmatic injection requires `scripting` and host access, supplied through `host_permissions` or temporary `activeTab` access. It targets the main frame by default; other frames require explicit targeting. [Chrome scripting API](https://developer.chrome.com/docs/extensions/reference/api/scripting)
- `content_scripts.matches` allows injection on matching hosts; `host_permissions` grants host access and `optional_host_permissions` can be granted at runtime. These declarations may produce permission warnings. [Chrome permission declarations](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)
- `activeTab` is granted through listed extension invocations: toolbar action, extension context menu, command shortcut, or omnibox suggestion. Access survives same-origin navigation but is revoked on navigation to another origin or tab closure. A click on an injected in-page button is not one of the listed grant mechanisms. **Implication:** explicit analysis consent and permission to place an inline action are separate concerns; the inline action needs an already available injection/access path. [Chrome activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)

## Official single-post lookup

X documents `GET https://api.x.com/2/tweets/{id}` for one post. The endpoint's raw OpenAPI lists OAuth 2.0 user tokens (`tweet.read`, `users.read`), OAuth 1.0a user tokens, and bearer tokens as alternatives. Its rendered reference describes `tweet.read` as including protected posts the user can see. [Single-post reference](https://docs.x.com/x-api/posts/get-post-by-id), [raw endpoint specification](https://docs.x.com/x-api/posts/get-post-by-id.md)

The lookup integration guide documents app-only bearer authentication for public posts, default `id`, `text`, and `edit_history_tweet_ids`, and optional fields/related-object expansions. It says edits create new IDs and lookup returns the most recent version. It also says deleted posts or protected posts from an account the authenticated user does not follow return `404` on single lookup. These are documented behaviors, not verified responses in this investigation. [Lookup integration guide](https://docs.x.com/x-api/posts/lookup/integrate)

The data dictionary describes `text` as UTF-8 post text, `note_tweet` as full text for long posts, `display_text_range` as the displayed portion, and optional `created_at`, `author_id`, `entities`, and `edit_controls`. Related posts/media are separate objects that can be expanded. **Implication:** a single-post text analysis need not retrieve thread, quoted-post, or media bodies. [X data dictionary](https://docs.x.com/x-api/fundamentals/data-dictionary)

**Documentation inconsistency:** the reviewed dictionary and lookup guide use `tweet.fields`, `note_tweet`, and `edit_history_tweet_ids`; the current generated endpoint reference/raw specification instead use `post.fields`, `note_post`, and `edit_history_post_ids`. The endpoint path remains `/2/tweets/{id}`. These spellings are evidence from the pages, not a validated request contract or an assertion that both forms work. [Dictionary](https://docs.x.com/x-api/fundamentals/data-dictionary), [lookup guide](https://docs.x.com/x-api/posts/lookup/integrate), [endpoint specification](https://docs.x.com/x-api/posts/get-post-by-id.md)

## Provenance and remaining uncertainties

- **Inference:** rendered-page extraction establishes what the extension read from that page at that time. It alone does not verify complete original post text, post/version identity, author identity, or agreement with X's API. A successful API response provides a platform-supplied text record for the returned ID/version; it does not establish the truth of the post's claims. This distinction follows from Chrome's shared-DOM access and X's structured lookup model. [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts), [X lookup](https://docs.x.com/x-api/posts/lookup/introduction)
- X's authentication guide limits app-only access to publicly available information. Browser login visibility is therefore not evidence of API authorization; protected access depends on the API's own user authorization context. [X authentication](https://docs.x.com/fundamentals/authentication/overview)
- The reviewed Chrome capability pages and X lookup/dictionary pages do not specify stable X browser selectors, post-container boundaries, or a browser DOM compatibility guarantee. This is limited to those reviewed pages, not a claim about every X document.
- No X browser surface, inline placement, selector, collapsed/expanded long post, quote exclusion, edited-post mapping, protected session, authenticated API call, or account entitlement was tested. DOM completeness and API field spelling remain implementation-validation questions. No credentials or accounts were used, and no access route or protected-post product behavior is selected here.
